# Job Project Manager Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an informational `project_manager` FK to `Job` and surface it (name + initials) across the job detail header, edit page, board/schedule chip, and job list, with a job-list filter by PM.

**Architecture:** A nullable `Job.project_manager` FK to `core.User` with no side effects. It rides existing job permissions (`can_manage_jobs` to edit). The serializer exposes a writable `project_manager` id plus a read-only `project_manager_name`; the board and schedule payloads add `project_manager_name`; the jobs list endpoint gains a `?project_manager=<id>` filter. The frontend renders the PM's name as a link to a PM-filtered job list, and renders **initials** (first + last word of the name) on the shared board/schedule chip. Initials are derived in the frontend from `project_manager_name` — no initials field on the API.

**Tech Stack:** Django 5.2 + DRF (MySQL test DB), Svelte 5 SPA (Vitest + @testing-library/svelte).

**Conventions to respect:**
- **Never write to the dev DB.** `makemigrations` is fine; `migrate` is the human's job. Tests use a separate auto-created test DB.
- TDD: failing test first, watch it fail, minimal code, watch it pass, commit.
- Run backend tests with `python manage.py test tests.<module>` from the repo root. **Never** run the full suite from parallel agents.
- Run frontend tests with `npm run test:run` from `frontend/` (never watch mode).
- User FK style: `'core.User'` (matches `Task.assignee`).

  function pmInitials(name) {
    if (!name) return '';

    if (parts.length === 0) return '';
    if (parts.length === 1) return parts[0][0].toUpperCase();
    return (parts[0][0] + parts[parts.length - 1][0]).toUpperCase();

```javascript
  import { api } from '../../lib/api.js';
  import JobList from '../../components/jobs/JobList.svelte';
  import { push, querystring } from 'svelte-spa-router';

  let jobs = $state([]);
  let count = $state(0);
  let page = $state(1);
  let loading = $state(true);
  let error = $state(null);

  let pmId = $derived(new URLSearchParams($querystring || '').get('pm') || '');
  let pmName = $derived(pmId && jobs.length ? jobs[0].project_manager_name : '');

  async function loadJobs() {
    loading = true;
    error = null;
    try {
      let url = `/api/jobs/?page=${page}`;
      if (pmId) url += `&project_manager=${pmId}`;
      const data = await api.get(url);
      jobs = data.results;
      count = data.count;
    } catch (e) {
      error = e.message;
    } finally {
      loading = false;
    }
  }

  function handleSelect(job) {
    push(`/jobs/${job.job_id}`);
  }

  // Reset to page 1 whenever the PM filter changes, then (re)load.
  $effect(() => {
    void pmId;
    page = 1;
  });

  $effect(() => {
    void page;
    void pmId;
    loadJobs();
  });
```

```svelte
{#if pmId}
  <h2>Jobs managed by {pmName || 'selected manager'} ({count})</h2>
{:else}
  <h2>Jobs ({count})</h2>
{/if}
```

> Note on the two `$effect`s: the first normalizes `page` back to 1 when the PM filter changes; the second performs the fetch. Keeping them separate avoids resetting `page` as a side effect of paging. If the reviewer prefers a single effect, fold the reset in — but verify paging still works after switching filters.
